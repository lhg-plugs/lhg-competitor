# lhg-cp-frame：竞品分析维度框架

> 目标：先搭好"看什么"的架子，再去找"看到了什么"。
> 核心纪律：**没有框架的情报搜集 = 信息垃圾场；先定维度，再动手。**

## 1. 何时使用

- 用户说"分析一下 XX 赛道的竞品"但没说看什么维度时 → 必须先跑本 skill 定框架
- 竞品名单已定、准备分工搜集情报前 → 用本 skill 输出"分析框架卡"，统一口径
- 赛道特殊（如 ToB、硬件、出海），默认五维不够用时 → 按第 5 步增减维度

## 2. 输入与输出

- **输入**：赛道描述 + 竞品名单（3-6 个）+ 我方产品（如有）
- **输出**：一份"分析框架卡"，包含：维度清单、每维度的可观测指标、信息来源清单、不看什么（明确排除项）

## 3. 第一步：确认分析目的

动手前先问清"这份分析用来干嘛"，目的不同，维度权重完全不同：

| 目的 | 权重倾斜 |
|---|---|
| 我方产品定位/差异化 | 产品、价格维度加权；口碑看差评集中点 |
| 定价策略参考 | 价格维度深挖：档位、计费方式、隐藏成本、折扣政策 |
| 渠道/增长策略参考 | 渠道、营销维度深挖；看它的获客主阵地 |
| 投资/合作尽调 | 五维全量 + 公司层面（融资、团队、合规） |
| 纯了解市场格局 | 五维轻量过一遍，不做深挖 |

目的没问清就开工，是最常见的返工原因。

## 4. 第二步：默认五维 + 可观测指标

除非第 5 步有明确理由增减，否则直接用默认五维。每个维度配 2-4 个**可观测**指标——"可观测"的意思是：不依赖竞品内部数据，公开渠道能验证。

### 维度一：产品
- 核心功能覆盖度（相对赛道主流功能清单，打勾/打叉）
- 差异化功能（它有别人没有的，列 1-3 个）
- 缺失功能（别人有它没有的，列 1-3 个）
- 体验口碑关键词（应用商店/社交媒体高频词，见维度五联动）

### 维度二：价格
- 免费版边界（能用到什么程度，卡点在哪）
- 付费档位与计费方式（按人头/按量/买断）
- 隐藏成本（实施费、 seats 上限、超量计费）
- 折扣与价格动作（近 12 个月涨价/降价/促销，需标日期）

### 维度三：渠道
- 获客主阵地（官网直销 / 应用商店 / 代理商 / 内容获客，排个序）
- 渠道伙伴（列出公开可查的合作伙伴）
- 地域覆盖（主攻市场，有无出海）

### 维度四：营销
- 内容策略（博客/视频/白皮书，更新频率）
- 品牌话术（官网首页第一句话，复制原话并标注来源）
- 投放痕迹（信息流广告、KOL 合作的可观测证据）

### 维度五：口碑
- 应用商店评分（分平台，标注"截至日期"）
- 差评集中点（归纳 Top 3 投诉）
- 社交媒体舆情关键词（正面/负面各 3 个）

## 5. 第三步：按赛道特性增减维度

| 赛道信号 | 增减动作 | 理由写法示例 |
|---|---|---|
| ToB / 企业服务 | **+ 服务与 SLA 维度**（实施周期、客服响应、SLA 承诺） | "ToB 采购决策中服务权重超 30%，默认五维覆盖不到" |
| 硬件 / 消费电子 | **+ 供应链与渠道维度**（代工、备货、线下渠道） | "硬件的交付能力决定生死，纯线上维度会漏看" |
| 出海产品 | **+ 合规与本地化维度**（GDPR、支付、语言） | "出海第一道坎是合规，不是功能" |
| 纯工具类小产品 | **− 渠道维度**（并入营销） | "小工具无独立渠道体系，单列会凑数" |

增减必须写理由进框架卡；无理由的增减一律视为凑数。

## 6. 第四步：输出分析框架卡

```markdown
# 分析框架卡：<赛道>（<日期>）
## 分析目的
<一句话：这份分析用来干嘛>
## 竞品名单（n 个）
1. <竞品 A> 2. <竞品 B> ...
## 维度与可观测指标
- 产品：<本赛道的具体指标，如"AI 笔记：语音转写准确率/多端同步延迟/模板生态">
- 价格：...
- 渠道：...
- 营销：...
- 口碑：...
- （增减维度及理由）
## 信息来源清单
- 官网/定价页、应用商店评论、媒体报道、招股书/财报（如有）
## 明确不看什么
- <如：不深挖技术架构、不做财务建模>（防范围蔓延）
## 时间敏感声明
- 价格/融资/评分等数据均标注"截至 <日期>"，过期需重验
```

框架卡必须给用户过目确认，确认后情报搜集才开工。

## 7. 框架卡评审清单（自查用）

框架卡写完后，逐条打勾，不满足的打回重写：

- [ ] 每个维度都有"本赛道的具体指标"，而不是通用描述
- [ ] 所有指标都是公开渠道可观测的（写出每个指标的预期来源）
- [ ] 维度增减写了理由，理由里有赛道特性（不是"我觉得"）
- [ ] 写了"明确不看什么"，且排除项是真实的诱惑项（不是凑数的）
- [ ] 时间敏感类指标标注了"截至日期"要求
- [ ] 一页纸能说清（超过一页说明没收敛）

### 不合格框架卡的三种死法

1. **维度是抄的，指标是空的**——"产品：看功能"这种等于没写。每个维度必须有本赛道的具体指标。
2. **没有排除项**——什么都想看，最后什么都看不深。"明确不看什么"是框架卡的灵魂。
3. **没经过用户确认**——框架卡是契约，不是自嗨。用户没点头就开工，返工自负。

## 8. 反模式（不要这么做）

- ❌ 跳过框架直接搜集情报——最后一定是一堆零散信息拼不起来
- ❌ 维度抄默认五维但不写"本赛道的具体指标"——等于没定框架
- ❌ 为了显得全面硬加维度（如给小工具加"供应链"）——凑数维度产出的一定是水货
- ❌ 框架卡不给用户确认——做到一半用户说"我想看的不是这个"，返工
- ❌ 指标不可观测（如"内部研发效率"）——公开渠道验证不了的指标不许进框架

## 9. 自检与反馈

每次执行完本 skill，做一次轻量自检：

1. 维度是否有增减？增减理由写了没？→ 没写理由的增减下次必须补。
2. 每个维度是否有"本赛道的具体指标"？→ 还停留在通用描述的，下次细化。
3. 是否明确写了"不看什么"？→ 没写容易范围蔓延。
4. 框架卡用户确认了吗？→ 未经确认不开工。

如发现本 skill 自身的方法论缺陷，按以下流程反馈：

- **标准冒烟用例**：用"AI 笔记应用赛道，竞品 Notion / 飞书文档 / 语雀 / Obsidian"走一遍本 skill，检查框架卡是否在 1 页内说清、指标是否可观测、增减理由是否成立。
- **一键提 issue**：确认问题后，以 `[QC] <一句话问题>` 为标题、正文写清"复现输入 → 错误输出 → 期望输出"，提交到 https://github.com/lhg-plugs/lhg-competitor/issues。
