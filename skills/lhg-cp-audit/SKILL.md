# lhg-cp-audit：竞品报告质检

> 目标：让每一份出去的报告都经得起"数据哪来的"三连问。
> 核心纪律：**脚本抓结构，人抓逻辑；blocker 清零才放行。**

## 1. 何时使用

- 竞品分析报告初稿完成后、交付用户前 → 必须跑一遍
- 收到一份别人写的竞品分析，想验证靠不靠谱时
- 流水线 Phase 4，本 skill 是出厂质检

## 2. 输入与输出

- **输入**：报告目录（含 1 份以上 .md 报告）
- **输出**：分级体检报告（blocker / warning / nit）+ "通过/不通过"结论

## 3. 第一步：跑确定性审计（机器）

```bash
python3 <插件目录>/scripts/audit/report_audit.py --target <报告目录> --format text
```

脚本规则（12 条，零第三方依赖）：

| 规则 | 级别 | 抓什么 |
|---|---|---|
| CP-DIM-001 | blocker | 分析维度缺失：产品/价格/渠道/营销/口碑覆盖不足 3 个 |
| CP-EVD-001 | blocker | 结论无来源：出现"数据显示/据报道"类断言却无来源节 |
| CP-SWOT-001 | blocker | SWOT 不完整：提到 SWOT 却缺 S/W/O/T 任一象限 |
| CP-ADV-001 | blocker | 建议与分析脱节：建议节未呼应报告中的任何分析维度 |
| CP-DIM-002 | warning | 对比矩阵单薄：表格数据行不足 3 行 |
| CP-DIM-003 | warning | 无对比矩阵：全文无 Markdown 表格 |
| CP-EVD-002 | warning | 来源过少：来源节链接不足 2 个 |
| CP-EVD-003 | warning | 数字断言缺出处：含百分比/金额断言却无来源节 |
| CP-SWOT-002 | warning | SWOT 条目单薄：四象限条目总数不足 8 条 |
| CP-ADV-002 | warning | 建议空泛：建议节只有"加强/提升"类泛词、无具体动作 |
| CP-DIM-004 | nit | 缺我方对照：全文无"我方/我们"对照视角 |
| CP-HON-001 | nit | 缺免责声明：无"仅供参考/不构成建议"类声明 |

分级语义：blocker = 报告现在发出去会误导人，必须修；warning = 修或写豁免理由；nit = 顺手修。

## 4. 第二步：人工评审（脚本抓不到的）

按以下清单逐条过，每条回答"是/否"，答"是"的必须改：

1. **编造数字**：有没有精确到小数点后两位、却无来源的数字？（如"市占率 23.47%"却无出处）
2. **措辞超证据**：有没有"碾压""第一""遥遥领先"这类词？有的话，证据撑得住吗？撑不住就降措辞。
3. **cherry-picking**：维度选择是否只挑了对我方有利的？（比如故意不看对手最强的维度）
4. **时间裸奔**：价格、融资、评分等时间敏感信息，是否都标了"截至日期"？
5. **来源质量**：来源是否全是自媒体/营销号？关键结论有没有至少一个一手来源（官网/财报/权威媒体）？
6. **建议可行性**：建议的代价是否在我方承受范围内？超出的话有没有写"需 X 资源"的前提？

## 5. 第三步：分级处理

- blocker：逐条修，修一条用脚本复查一条；修不掉的（如实在找不到来源）转入报告"信息缺口"节并降级措辞，不许硬留。
- warning：修掉，或在体检报告里写豁免理由（为什么这次可以不修）。
- nit：顺手修，不修也要在报告里记一笔。

**为清零而改审计规则 = 作弊**，发现一次，之前所有的"通过"结论全部作废重审。

### 修复手册：四类 blocker 怎么修

- **CP-DIM-001（维度缺失）**：补维度情报；实在没信息就写"本维度未覆盖，理由：…"进"信息缺口"，但覆盖不足 3 个时不许豁免。
- **CP-EVD-001（结论无来源）**：两种修法——找到来源补上，或删掉断言/降为"待验证的假设"。不许把"数据显示"改成"感觉"糊弄。
- **CP-SWOT-001（象限不完整）**：补象限条目；某象限确实无信息时写"暂未发现（已搜 <渠道>）"，不许凑数编条目。
- **CP-ADV-001（建议脱节）**：重写建议，每条开头先写"← 矩阵第 X 行"；写不出来说明这条建议本来就不该存在，直接删。

## 6. 第四步：体检报告模板

```markdown
# 体检报告：<报告名>（<日期>）
## 结论：通过 / 不通过
## blocker（n）
- [CP-XXX-000] <标题>：<位置> —— 处理：已修/转信息缺口
## warning（n）
- [CP-XXX-000] <标题>：<位置> —— 处理：已修/豁免（理由）
## nit（n）
- ...
## 人工评审 6 问
1. 编造数字：否 ……
## 需人工处理
- <脚本和人都搞不定的，列出来给用户>
```

结论只能是"通过"或"不通过"，不许写"基本通过""大致没问题"。

## 7. 审计记录留存

每次体检的产出物都要留档，方便追溯"这份报告当时为什么放行"：

- 体检报告存 `reports/audit-YYYYMMDD-<报告名>.md`
- 脚本 JSON 输出存 `reports/audit-YYYYMMDD-<报告名>.json`（`--format json` 重定向）
- 豁免项单独列表：规则 ID + 理由 + 豁免人 + 有效期（如"价格数据豁免，3 个月后重审"）

审计记录是插件的"质量账本"：用户问"这份报告靠谱吗"，把当时的体检报告翻出来，比口头保证管用。

### 豁免的边界

warning 可以豁免，但三类情况不许豁免，直接打回重做：

1. **来源造假嫌疑**：链接打不开、来源与结论对不上——这是诚信问题，不是质量问题。
2. **核心维度系统性缺失**：比如 ToB 报告完全不看价格——框架错了，修框架。
3. **同一份报告第三次豁免同一条规则**：说明不是"这次特殊"，是流程有问题，停下来修流程。

### 给用户的"食用说明"

体检通过的报告，交付时附三句话，管理用户预期：

1. "这份报告基于公开信息，X 个格子是'未公开'（见信息缺口节）。"
2. "价格/评分类数据截至 <日期>，做决策前建议重验。"
3. "建议的代价是估算，落地前请按我方实际资源重算。"

质检的终点不是"报告完美"，是"用户清楚报告的边界在哪"。

## 8. 反模式（不要这么做）

- ❌ 只跑脚本不做人工评审——脚本看不懂"措辞超证据"，这是人肉环节
- ❌ blocker 转 warning 靠改措辞糊弄（如把"数据显示"改成"感觉"）——换汤不换药
- ❌ 豁免理由写"时间紧"——时间紧不是质量豁免理由，写清楚"为什么这次不修也行"
- ❌ 体检报告只给结论不给清单——用户要看到每条发现的处理情况
- ❌ 一份报告审完，所有历史报告自动"通过"——每份独立审

## 9. 自检与反馈

每次执行完本 skill，做一次轻量自检：

1. 脚本和人工评审都做了吗？→ 只做一半等于没做。
2. blocker 是否真的清零（重跑脚本验证）？→ 口头说清零不算数。
3. 豁免理由是否写清楚了"为什么这次可以不修"？→ "时间紧"不算理由。
4. 结论是二选一吗？→ 出现"基本通过"打回重写。

如发现本 skill 自身的方法论缺陷，按以下流程反馈：

- **标准冒烟用例**：拿一份故意埋了"无来源断言 + SWOT 缺威胁象限 + 建议空泛"的报告走一遍本 skill，检查脚本是否命中、人工 6 问是否问出来。
- **一键提 issue**：确认问题后，以 `[QC] <一句话问题>` 为标题、正文写清"复现输入 → 错误输出 → 期望输出"，提交到 https://github.com/lhg-plugs/lhg-competitor/issues。
